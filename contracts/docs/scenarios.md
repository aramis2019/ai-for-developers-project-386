# Пользовательские сценарии Meetly

Документ фиксирует основные user journeys, по которым проверяется работа сервиса.
Каждый сценарий описан шагами и критериями приёмки; критерии проверяются
автоматически в `backend/tests/Meetly.IntegrationTests` и вручную через UI.

Термины: **Гость** — анонимный посетитель, **Владелец** — единственный профиль
владельца календаря (`GET /api/admin/profile`). Все моменты времени — UTC,
формат ISO 8601 с суффиксом `Z` (см. `contracts/docs/domain.md` §2).

## Сценарий 1 (гость): успешная запись на встречу

**Предусловие:** в системе есть хотя бы один тип события; в текущем окне
14 суток есть свободные слоты.

**Шаги:**

1. Гость открывает публичную страницу и видит список типов встреч
   (`GET /api/event-types` → `200`, `PublicEventTypeList`).
2. Гость выбирает тип события и получает сетку свободных слотов
   (`GET /api/event-types/{id}/slots` → `200`, `SlotsPage`).
3. Гость выбирает слот, заполняет имя и e-mail, отправляет форму
   (`POST /api/bookings` → `201`, `Booking`).

**Критерии приёмки:**

- В ответе бронирования `id` — валидный UUID, `start`/`end` совпадают с выбранным
  слотом, `eventTypeTitle` подставлен из типа события.
- Бронь появляется в `GET /api/admin/bookings` (сортировка по `start`).
- Слот, занятый бронью, исчезает из последующих ответов `/slots`.

**Автотест:** `EndToEnd_HappyPath_GuestBookingFlow` (см. `IntegrationTests`).

## Сценарий 2 (гость): гонка за слот → `409 SLOT_ALREADY_BOOKED`

**Предусловие:** есть свободный слот, выбранный гостем.

**Шаги:**

1. Первый гость завершает бронирование слота (`201`).
2. Второй гость успел загрузить старую сетку слотов, отправляет `POST /api/bookings`
   с тем же `start`.

**Критерии приёмки:**

- Второй запрос отвечает `409` с телом `{ code: "SLOT_ALREADY_BOOKED", ... }`.
- В БД остаётся ровно одна бронь на этот интервал.
- UI при `409` перезапрашивает `/slots` и просит выбрать другое время
  (клиентское поведение из `frontend/src/api/errors.ts` — `isSlotConflict`).

**Автотест:** `CreateBooking_DuplicateSlot_Returns409`.

**Инвариант ADR 0001:** проверка занятости и вставка атомарны. На Postgres
это гарантирует exclusion constraint `EXCLUDE USING gist (during WITH &&)`
на generated `tstzrange`-колонке; на InMemory — `lock` вокруг проверки-вставки.

## Сценарий 3 (гость): валидация ввода → `422`

Ветвится по конкретному нарушению — клиент показывает пользователю разную
подсказку по полю `code` (см. ADR 0002).

| Ситуация | Пример | HTTP | `code` |
| --- | --- | --- | --- |
| `start` не выровнен по шагу сетки | `09:15` при шаге 30 мин | 422 | `SLOT_NOT_ALIGNED` |
| Встреча выходит за рабочие часы | 60-минутный слот в `17:30` | 422 | `SLOT_OUTSIDE_WORKING_HOURS` |
| Слот в прошлом или дальше 14 дней | `start = now - 1h` | 422 | `SLOT_OUT_OF_WINDOW` |
| Некорректные контакты гостя | `email = "not-email"` | 422 | `VALIDATION_FAILED` |

**Критерии приёмки:** каждый случай возвращает свой `code`; при получении `422`
UI не перезапрашивает `/slots`, а подсвечивает поле формы.

**Автотесты:** `CreateBooking_MisalignedSlot_Returns422` + новые сквозные
проверки в user-journey тесте.

## Сценарий 4 (гость): тип события исчез → `404 EVENT_TYPE_NOT_FOUND`

Возможен, если владелец пересоздал тип или гость держал старую ссылку.

**Шаги:** `POST /api/bookings` с `eventTypeId`, которого нет.

**Критерии приёмки:** `404`, `code = EVENT_TYPE_NOT_FOUND`. Клиент возвращает
гостя на список видов брони.

**Автотест:** `CreateBooking_NonExistentEventType_Returns404`.

## Сценарий 5 (владелец): создать тип события

**Шаги:**

1. Владелец открывает админку типов событий (`GET /api/admin/event-types` → `200`).
2. Заполняет форму (id-slug, название, описание, длительность 5–480 минут).
3. Отправляет `POST /api/admin/event-types` → `201`, `EventType`.

**Критерии приёмки:**

- Создание с валидным id возвращает `201` и объект с проставленным `createdAt`.
- Создание с занятым id возвращает `409 EVENT_TYPE_ALREADY_EXISTS`.
- Тип сразу виден и в админском (`GET /api/admin/event-types`),
  и в публичном (`GET /api/event-types`) списках.

**Автотесты:** `CreateEventType_Success_Returns201`,
`CreateEventType_DuplicateId_Returns409`.

## Сценарий 6 (владелец): посмотреть предстоящие встречи

**Шаги:** владелец открывает `/admin/bookings` (`GET /api/admin/bookings` → `200`,
`BookingList`).

**Критерии приёмки:**

- Список содержит все брони с `start >= now`, отсортирован по `start` возрастанию.
- Каждая строка содержит `eventTypeTitle`, `start`, `end`, `guest`, `durationMinutes`.
- Прошедшие брони в список не попадают.

**Автотест:** `GetAdminBookings_AfterCreating_ReturnsBooking`.

## Сценарий 7 (администратор): сквозная занятость по всем типам событий

Ключевой инвариант ADR 0001: бронь одного типа события блокирует пересекающиеся
слоты во **всех** остальных типах.

**Шаги:**

1. Создать тип события A (30 минут) и тип B (60 минут).
2. Забронировать в A слот `09:00–09:30`.
3. Запросить слоты типа B на тот же день.

**Критерии приёмки:**

- Слот B `09:00–10:00` отсутствует (пересекается с бронью A).
- Слот B `08:00–09:00` тоже отсутствует, если пересекается.
- Первый свободный слот B — `09:30–10:30` (после конца брони A).

**Автотест:** `CrossEventType_BookingA_BlocksOverlappingSlotsInB`.

## Границы (что сознательно вне сценариев)

Соответствует `contracts/docs/domain.md` §5:

- отмена/перенос брони; редактирование/удаление типа события;
- регистрация, вход, роли, права доступа;
- часовые пояса, отличные от UTC; индивидуальное расписание по дням;
- уведомления на почту, интеграции с внешними календарями.

Появление этих сценариев начинается с изменения `contracts/spec/*.tsp`
(см. правило 1 в `AGENTS.md`), а не с UI или бэкенда.
