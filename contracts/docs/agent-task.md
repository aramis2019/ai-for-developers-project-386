# Постановка задачи агенту

Промпт, по которому AI-агент готовит TypeSpec-спецификацию API-контракта.
Формулировка самодостаточна: агенту не нужен дополнительный контекст, кроме этого файла.

---

## Роль

Ты — API-дизайнер. Твоя задача — зафиксировать контракт сервиса записи на встречи
в виде TypeSpec-спецификации и сгенерировать из неё OpenAPI 3.1.
Реализацию бизнес-логики писать не нужно — только контракт.

## Контекст предметной области

Сервис записи на встречи к **одному** владельцу календаря.

Роли:

- **Владелец календаря** — единственный заранее заданный профиль. Регистрации и авторизации в системе нет, админская часть работает от имени этого профиля.
- **Гость** — анонимный посетитель, бронирует слот без создания аккаунта и без входа.

Сценарии владельца:

1. Создать тип события, указав `id`, название, описание и длительность в минутах. Идентификатор задаёт сам владелец.
2. Посмотреть страницу предстоящих встреч — единый список бронирований всех типов событий.

Сценарии гостя:

1. Посмотреть список видов брони: название, описание, длительность.
2. Выбрать тип события и открыть календарь свободных слотов на ближайшие 14 дней.
3. Создать бронирование на выбранный слот, указав контактные данные.

## Правила, которые контракт обязан зафиксировать

1. **Сквозная занятость.** Два бронирования не могут пересекаться по времени, даже если относятся к разным типам событий. Интервал встречи — полуинтервал `[start, end)`.
2. **Окно записи.** Слоты формируются на 14 суток, начиная с текущего момента. Окно скользящее и пересчитывается на каждый запрос. Записаться можно только на слот целиком внутри окна.
3. **Сетка слотов.** Рабочие часы владельца — `09:00–18:00` UTC, все дни недели. Шаг сетки — 30 минут. Слот валиден, если `[start, start + durationMinutes)` целиком помещается в рабочие часы тех же суток.
4. **Время.** Все моменты времени — UTC, ISO 8601 с суффиксом `Z`. Часовой пояс в текущей версии всегда `UTC`.
5. **Слот — вычисляемая сущность.** Отдельно не хранится, строится на лету из рабочих часов, шага сетки, длительности типа события и множества существующих броней.
6. **Длительность фиксируется в брони.** Изменение типа события не влияет на уже созданные бронирования.

## Требования к результату

### Доменные модели

Опиши сущности: `Owner`, `WorkingHours`, `EventType`, `PublicEventType`, `Slot`,
`BookingWindow`, `Guest`, `Booking` и модели запросов/ответов к ним.

Для каждого поля укажи:

- ограничения (`@minLength`, `@maxLength`, `@minValue`, `@maxValue`, `@pattern`, `@format`);
- doc-комментарий на русском языке, объясняющий смысл поля, а не повторяющий его название;
- `@example` для полей, где формат неочевиден.

Выдели переиспользуемые скалярные типы: `EventTypeId` (slug `^[a-z0-9]+(?:-[a-z0-9]+)*$`),
`BookingId` (UUID), `TimeOfDay` (`HH:mm`), `Email`.

### Операции

| Сценарий | Метод и путь |
| --- | --- |
| Профиль владельца | `GET /api/admin/profile` |
| Список типов событий (админ) | `GET /api/admin/event-types` |
| Создать тип события | `POST /api/admin/event-types` |
| Предстоящие встречи | `GET /api/admin/bookings` |
| Виды брони (гость) | `GET /api/event-types` |
| Свободные слоты типа события | `GET /api/event-types/{eventTypeId}/slots` |
| Создать бронирование | `POST /api/bookings` |

Раздели операции на два namespace с тегами `Admin` и `Public`.
Для каждой операции задай `@summary` и doc-комментарий с описанием алгоритма
и порядка проверок.

### Ошибки

Единое тело ошибки `ErrorBody`: `code` (машиночитаемый), `message` (для пользователя),
`details` (необязательный контекст). Коды и статусы:

| Код | HTTP | Когда |
| --- | --- | --- |
| `BAD_REQUEST` | 400 | Не разобрано тело, неверный формат даты |
| `EVENT_TYPE_NOT_FOUND` | 404 | Тип события не существует |
| `EVENT_TYPE_ALREADY_EXISTS` | 409 | `id` типа события занят |
| `SLOT_ALREADY_BOOKED` | 409 | Интервал пересекается с существующей бронью |
| `SLOT_OUT_OF_WINDOW` | 422 | Слот вне окна 14 суток или в прошлом |
| `SLOT_NOT_ALIGNED` | 422 | `start` не выровнен по шагу сетки |
| `SLOT_OUTSIDE_WORKING_HOURS` | 422 | Встреча не помещается в рабочие часы |
| `VALIDATION_FAILED` | 422 | Нарушены доменные правила |

Каждая операция объявляет union из успешного ответа и применимых ошибок.
Успешное создание возвращает `201` с телом созданного ресурса.

### Структура проекта

```
contracts/main.tsp          — сервис, версия, сервер, импорты
contracts/spec/errors.tsp   — коды ошибок и модели ответов с ошибками
contracts/spec/models.tsp   — скалярные типы и доменные модели
contracts/spec/admin.tsp    — операции владельца календаря
contracts/spec/public.tsp   — операции гостя
contracts/tspconfig.yaml    — эмиттер @typespec/openapi3, вывод в contracts/dist
```

## Ограничения

Не добавляй в контракт то, чего нет в требованиях:

- аутентификацию, токены, роли и права доступа;
- редактирование и удаление типов событий;
- отмену и перенос бронирования;
- пагинацию, фильтры и сортировку через query-параметры;
- часовые пояса, отличные от UTC, и настройку расписания по дням недели.

## Критерии приёмки

1. `npx tsp compile . --warn-as-error` завершается без ошибок и предупреждений.
2. `npx tsp format "**/*.tsp"` не меняет файлы.
3. Сгенерирован валидный `contracts/dist/openapi.yaml` версии OpenAPI 3.1.
4. В спецификации ровно 7 операций из таблицы выше, без лишних.
5. Каждое правило из раздела «Правила» отражено либо в ограничениях типов, либо в doc-комментарии операции.
6. Ни одна модель не содержит полей, не описанных в этом задании.
