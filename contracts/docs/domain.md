# Доменная модель

Приложение: сервис записи на встречи к одному владельцу календаря (условное имя — **Meetly**).
Документ фиксирует внешнее поведение системы: сущности, их поля, инварианты и сценарии.
Машиночитаемая версия контракта — `contracts/main.tsp` + `contracts/spec/*.tsp`,
сгенерированный OpenAPI — `contracts/dist/openapi.yaml`.

## 1. Роли

| Роль | Как определяется | Что доступно |
| --- | --- | --- |
| Владелец календаря | Единственный заранее заданный профиль. Создаётся при инициализации системы, через API не создаётся и не удаляется. | Админская часть `/api/admin/*` |
| Гость | Анонимный посетитель. Аккаунта нет, вход не выполняется, состояние между запросами не хранится. | Публичная часть `/api/*` |

Регистрации и авторизации в системе нет. Любой запрос к админской части
выполняется от имени владельца календаря — сервер подставляет его профиль сам.

## 2. Общие соглашения

- **Время.** Все моменты времени в API — UTC, ISO 8601 с суффиксом `Z`: `2026-08-17T09:30:00Z`.
  Перевод в локальный часовой пояс пользователя — задача клиента.
- **Интервал встречи** — полуинтервал `[start, end)`. Встречи `09:00–09:30` и `09:30–10:00` не пересекаются.
- **Пересечение интервалов.** `A` и `B` пересекаются, если `A.start < B.end && B.start < A.end`.
- **Окно записи** — `[now, now + 14 суток]`, где `now` — момент обработки запроса.
  Окно скользящее: оно пересчитывается на каждый запрос, а не фиксируется в конфигурации.

## 3. Сущности

### 3.1. Владелец календаря (`Owner`)

Настройки, по которым строится расписание. Синглтон, доступен только для чтения.

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | `string` | Стабильный идентификатор профиля, например `owner`. |
| `name` | `string`, 1–120 | Отображаемое имя на публичных страницах. |
| `email` | `email` | Контактный адрес владельца. |
| `timeZone` | `"UTC"` | Часовой пояс расписания. В текущей версии всегда `UTC`. |
| `workingHours.start` | `HH:mm` | Начало рабочего дня. По умолчанию `09:00`. |
| `workingHours.end` | `HH:mm` | Конец рабочего дня. По умолчанию `18:00`. |
| `slotStepMinutes` | `int32` | Шаг сетки слотов. По умолчанию `30`. |
| `bookingWindowDays` | `int32` | Глубина окна записи в сутках. По умолчанию `14`. |

Инварианты:

- `workingHours.end > workingHours.start`;
- рабочие часы одинаковы для всех дней недели, включая выходные;
- профиль всегда существует — эндпоинт профиля не возвращает `404`.

### 3.2. Тип события (`EventType`)

Вид встречи, который владелец предлагает гостям.

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | slug, 1–64 | Задаётся владельцем вручную, `^[a-z0-9]+(?:-[a-z0-9]+)*$`, например `intro-call`. Участвует в публичных ссылках. |
| `title` | `string`, 1–120 | Название для гостя. |
| `description` | `string`, 0–1000 | Описание встречи. |
| `durationMinutes` | `int32`, 5–480 | Длительность встречи в минутах. |
| `createdAt` | `utcDateTime` | Момент создания. Проставляется сервером. |

Инварианты:

- `id` уникален в пределах системы; повторное создание — конфликт, существующий тип не перезаписывается;
- длительность не влияет на уже созданные бронирования: каждая бронь хранит собственное `durationMinutes`, зафиксированное в момент записи.

Гостю тип события отдаётся в урезанном виде (`PublicEventType`): `id`, `title`, `description`, `durationMinutes`.

### 3.3. Слот (`Slot`)

**Вычисляемая сущность, в хранилище не существует.** Слот — это интервал-кандидат
для встречи конкретного типа события. Список слотов всегда строится на лету и
действителен только на момент ответа.

| Поле | Тип | Описание |
| --- | --- | --- |
| `start` | `utcDateTime` | Начало слота, выровнено по сетке. |
| `end` | `utcDateTime` | `start + durationMinutes` выбранного типа события. |

Алгоритм построения сетки для типа события `T`:

1. Взять окно `[now, now + 14 суток]`.
2. Для каждых суток окна расставить точки старта внутри `workingHours` с шагом `slotStepMinutes`,
   начиная с `workingHours.start`.
3. Оставить точку, если интервал `[start, start + T.durationMinutes)` целиком помещается
   в рабочие часы **тех же суток** (`start + duration <= workingHours.end`).
4. Оставить точку, если интервал целиком лежит внутри окна записи (`start >= now`, `end <= now + 14 суток`).
5. Отбросить точки, чей интервал пересекается **с любым** существующим бронированием,
   независимо от того, к какому типу события оно относится.

Следствия:

- сетка зависит от типа события: при `durationMinutes = 60` и рабочем дне до `18:00`
  последний слот начинается в `17:00`, при `durationMinutes = 30` — в `17:30`;
- одна бронь может «съесть» несколько соседних слотов, если её длительность больше шага сетки;
- слоты не «резервируются» просмотром: между получением списка и отправкой формы слот может занять другой гость.

### 3.4. Бронирование (`Booking`)

Подтверждённая запись гостя на конкретный интервал.

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | `uuid` | Генерируется сервером. |
| `eventTypeId` | slug | Тип события. |
| `eventTypeTitle` | `string` | Название типа события — денормализовано, чтобы список встреч рисовался одним запросом. |
| `start` | `utcDateTime` | Начало встречи. |
| `end` | `utcDateTime` | Конец встречи, вычисляется сервером. |
| `durationMinutes` | `int32` | Длительность, зафиксированная при бронировании. |
| `guest.name` | `string`, 1–120 | Имя гостя. |
| `guest.email` | `email` | Почта гостя. |
| `guest.note` | `string?`, 0–1000 | Необязательный комментарий. |
| `createdAt` | `utcDateTime` | Момент создания брони. |

Гость (`Guest`) — не самостоятельная сущность, а value-object внутри брони:
аккаунт не создаётся, две брони с одинаковым e-mail не связываются между собой.

### 3.5. Ключевой инвариант — сквозная занятость

> Никакие два бронирования в системе не пересекаются по времени, даже если относятся к разным типам событий.

Формально: для любых двух броней `A ≠ B` верно `A.end <= B.start || B.end <= A.start`.

Инвариант проверяется по всему множеству броней, а не в разрезе типа события.
Проверка занятости и запись выполняются атомарно, чтобы при гонке двух гостей
за один слот успешным был ровно один запрос.

## 4. Сценарии

### 4.1. Владелец: создать тип события

1. Владелец открывает админскую часть, вводит `id`, название, описание и длительность.
2. Система проверяет формат полей и уникальность `id`.
3. Тип события создан и сразу появляется на публичной странице видов брони.

Отказы: занятый `id` → `409 EVENT_TYPE_ALREADY_EXISTS`; неверный формат `id` или длительность
вне диапазона → `422 VALIDATION_FAILED`.

### 4.2. Владелец: посмотреть предстоящие встречи

1. Владелец открывает страницу предстоящих встреч.
2. Система возвращает **единый** список броней всех типов событий, у которых `start >= now`,
   отсортированный по `start` по возрастанию.
3. Каждая строка содержит время, длительность, название типа события и контакты гостя.

Прошедшие встречи в этот список не попадают. Пустой список — валидное состояние.

### 4.3. Гость: записаться на встречу

1. Гость открывает публичную страницу и видит список видов брони: название, описание, длительность.
2. Выбирает тип события — открывается календарь на 14 дней вперёд.
3. Система показывает только свободные слоты выбранного типа события.
4. Гость выбирает слот, вводит имя, e-mail и, при желании, комментарий.
5. Система повторно проверяет доступность слота и создаёт бронь.
6. Гость получает подтверждение с точным временем встречи.

Отказы на шаге 5:

| Ситуация | Ответ |
| --- | --- |
| Типа события больше нет | `404 EVENT_TYPE_NOT_FOUND` |
| Слот заняли, пока гость заполнял форму | `409 SLOT_ALREADY_BOOKED` |
| `start` не выровнен по шагу сетки | `422 SLOT_NOT_ALIGNED` |
| Встреча выходит за окно 14 суток или начинается в прошлом | `422 SLOT_OUT_OF_WINDOW` |
| Встреча не помещается в рабочие часы | `422 SLOT_OUTSIDE_WORKING_HOURS` |
| Некорректные контактные данные | `422 VALIDATION_FAILED` |

Рекомендуемое поведение клиента при `409`: перезапросить слоты и попросить выбрать другое время.

## 5. Границы текущей версии

Сознательно **не входит** в контракт:

- регистрация, вход, роли и права доступа;
- редактирование и удаление типов событий;
- отмена и перенос бронирования;
- индивидуальное расписание по дням недели, перерывы, отпуска, блокировки времени;
- буферы между встречами и лимит встреч в день;
- уведомления на почту, интеграции с внешними календарями;
- пагинация списков и часовые пояса, отличные от UTC.

Эти пункты — кандидаты на следующие версии контракта; текущие модели расширяются
без ломающих изменений.

## 6. Карта контракта

| Сценарий | Метод и путь | Ответ |
| --- | --- | --- |
| Профиль владельца | `GET /api/admin/profile` | `Owner` |
| Список типов событий (админ) | `GET /api/admin/event-types` | `EventTypeList` |
| Создать тип события | `POST /api/admin/event-types` | `201 EventType` |
| Предстоящие встречи | `GET /api/admin/bookings` | `BookingList` |
| Виды брони (гость) | `GET /api/event-types` | `PublicEventTypeList` |
| Свободные слоты | `GET /api/event-types/{eventTypeId}/slots` | `SlotsPage` |
| Создать бронирование | `POST /api/bookings` | `201 Booking` |

Все ошибки возвращают единое тело `ErrorBody` с машиночитаемым полем `code`.
